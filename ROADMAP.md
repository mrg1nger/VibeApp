Everything recommended so far, in one place. Tick items off as they ship.

## Bigger features

- [x] **Cline as a third agent (ClinePass).** Add the Cline CLI alongside Claude and Codex, signed in with a ClinePass subscription ($9.99/month flat, open-weight models such as Qwen, GLM, Kimi and DeepSeek, its own 5-hour/weekly/monthly limits, separate from the Claude and Codex plans). What it would add:
  - a cheap place for straightforward implementation work Claude would otherwise spend its own plan on;
  - a more independent second reviewer (a different model family from Claude and Codex);
  - a fallback when Claude's limit is reached (order: Claude, then Codex, then Cline).

  Start with a trial before building anything (needs `npm i -g cline` and the user's own ClinePass sign-in): run it on real tasks with `--json`, and check three unknowns:
  - **Safety:** auto-approval is on by default and no sandbox or read-only mode has been found, so check whether plan mode (`-p`) truly blocks edits before using it as a reviewer; until then keep it behind Go Nutz or undo snapshots, since VibeApp's destructive-command prompts don't cover it.
  - **Shared memory:** whether `cline mcp` / `--config <dir>` can give it the vibe_memory tools per run.
  - **Windows:** whether it can be launched hidden (no console-window flashes, as fixed for Codex).

  Also unknown: no usage API found (dashboard only), so possibly no third meter; model list churns; quality on hard multi-file work is expected to be below Claude and Codex (untested). Check ClinePass terms before selling VibeApp with it built in. Docs: [ClinePass](https://docs.cline.bot/getting-started/clinepass), [CLI](https://docs.cline.bot/cline-cli/getting-started).

  **Built (0.3.0, 2026-11-09).** Trial findings, against cline 3.0.74 on Windows:
  - `--hooks-dir` is ignored; `CLINE_DIR` gives VibeApp its own Cline folder (hook, settings), while `CLINE_DATA_DIR` keeps the user's sign-in.
  - Piped stdin isn't seen, and an open stdin pipe makes every run hang, so the prompt goes on the command line (or in a task file past 20,000 characters).
  - Plan mode (`-p`) still runs shell commands, so it isn't a read-only mode by itself.
  - Cline offers the user's account connectors (Composio: Gmail, Drive, Docs). With its editor off, it went looking for a Drive tool to edit a file with.
  - Tool servers are started through a shell, so any space in a path breaks them.
  - No usage API: the CLI reports tokens per run, but not the plan's limits.

  What was built:
  - `clineExec.ts` runner.
  - The PreToolUse hook (`hookPolicy.ts`): an allow-list per mode (build, review, background job). It confines work to the project and swaps destructive commands for a "BLOCKED" echo, and it checks itself before every run.
  - The connector tools switched off by name.
  - Shared memory with the paths passed in the environment.
  - `run_cline_subtask`, with Codex reviewing Cline's work.
  - Routing notes when Codex or Claude is low.
  - Cline as the last takeover after Codex.
  - Background jobs (scribe, summary, tidy, brief, code map) on Cline, with Haiku as the fallback.
  - A Settings section with Test Cline.
  - Usage log and report columns.
  - 14 unit tests and 11 live smoke tests; `VIBEAPP_EVAL_BUILDER=cline` and `npm run eval -- helpers`.

  First evals (2026-11-09):
  - **Teamwork eval, Cline building (Sonnet):** all 3 tasks work. Claude's cost is about the same as with Codex (265k vs 262k weighted). Cline uses more tokens than Codex, but on its own plan (feature 223k vs Codex 71k) and takes slightly longer (1.7-2.6 min).
  - **Memory-saving cases:** Haiku 5/5, Qwen3.7 Plus 5/5, GLM-5.3 Flash 5/5, DeepSeek V4.1 Flash 4/5 (missed "in every project" as a global rule).

  Still open:
  - Watch real use (usage report → Cline) before routing more than "simple, well-specified" work to Cline.
  - Whether to pin a background-job model (now Cline's own default, Qwen3.7 Plus on this account; DeepSeek did worse).
  - Cline as a second reviewer (review mode now exists and can't change files).
  - A ClinePass meter, if Cline ever exposes the limits.
  - Check ClinePass terms before selling VibeApp with it built in.
- [ ] **Custodial jobs off Claude's plan.** On DevBox, compaction, tidy, scribe and brief took about 12% of Claude's weighted usage over 7 days, plus the Haiku route judge. They're short and repetitive, so a small model could do them. Cheapest path first:
  1. ClinePass models: **done in 0.3.0** for scribe, summary, tidy, brief and code map. Left on Claude: the route judge (it needs an answer in under 5 s; a Cline run starts cold in 4-12 s) and compaction (Claude compacting its own conversation).
  2. Or a small off-the-shelf local model (e.g. a 1–4B Qwen through Ollama). Needs a check of the GPU on DevBox.
  3. Fine-tune one on VibeApp's own past helper outputs, only if 1 and 2 aren't good enough.

  Training a model from scratch isn't worth it. Measure every option with an eval of the helper jobs (same input, compare against Haiku's output) before switching over.
- [ ] **Starter templates** (#8). "A website," "a game," "a Discord bot" instead of a blank folder, ready for the preview and Publish.
- [ ] **Automatic app updates.** VibeApp downloads new versions itself instead of reinstalling from a zip. Needs somewhere to host releases, e.g. GitHub Releases.
- [ ] **Self-editing with a safety net.** Open VibeApp's own source as a project, have Claude change it, then "Rebuild & restart," keeping the last working version and rolling back automatically if the new one won't start.
- [ ] **Preview for Python apps.** Flask, Django, Streamlit and the like currently show "Nothing to preview."
- [ ] **Open-sourcing VibeApp (on hold).** Selling it as is looks unlikely: it runs on the user's Claude and ChatGPT subscription sign-ins, which Anthropic's Agent SDK terms don't allow third-party products to offer without approval (check the current wording, and OpenAI's), and free first-party apps overlap heavily. Open source avoids most of that, since each user brings their own subscriptions. A security check (2026-10-28) found nothing that risks the user's accounts:
  - no real keys anywhere in the 80 commits;
  - commits use GitHub's private email;
  - the installer holds only the built app;
  - sign-ins, secrets and tokens all live outside the repo.

  A second check (2026-11-09, 0.3.1) found no secrets in the 85 commits and fixed three weak spots (links could open any program handler, pairing guesses were capped only per address, DNS rebinding in "This computer" mode), updated the dependencies with known problems, and trimmed the node-pty patch (older commits still hold its build files with the user's folder names; harmless, but a history rewrite would remove them).

  Before making it public:
  - decide whether `package.json`'s author "Chris" and ROADMAP's DevBox/MRG-PC/"yay" mentions can stay;
  - add a LICENSE (MIT is the usual choice);
  - post only the current setup.exe, not the old `release\VibeApp-0.1.0-installer.zip`;
  - turn on GitHub secret scanning.

## Loose ends to check

- [ ] **Keep measuring.** The usage log exists now; compare a week of real use with the scribe, hand-off resume and (if tried) fresh sessions on, and decide the defaults from the numbers. So far only small tests: on a task with durable facts the scribe cut Claude's steps from 4 to 2-3 and its cached reads by 30-55%, at about 1.8k Haiku tokens.
- [ ] **Scribe quality.** Haiku sometimes over-saves (task-only instructions as preferences) or fills in typical details. Mitigated with stricter rules, a check that numbers must appear in the exchange, and retiring (not overwriting) corrected facts, but watch the "Saved automatically" facts on the Memory screen.
- [ ] **Fresh-session summaries lose detail.** Off by default; needs real long-project use before it's worth enabling.
- [ ] **Run the same checks after Claude's own edits.** They only run after Codex hand-offs today.
- [ ] **Code map accuracy on big projects.** Capped at 600 files, 80 summarised per run, only the first ~1,200 characters of each file are read; large or unusual projects may be mapped partially.
- [ ] **Real GitHub backup.** Vercel publishing is confirmed working on the VM; the GitHub side (install, sign-in, first push, "Get a project from GitHub") hasn't had a real run against github.com. Backup, the newer-work banner and both conflict choices are tested against a stand-in for GitHub (a repository on disk); the GitHub CLI isn't signed in on MRG-PC.
- [ ] **No window flashes during Codex reviews and hand-offs.** Fixed for the usage check; not yet tested while Codex runs its own commands.
- [ ] **Allow/Deny banner queue.** The logic is tested, but nobody has clicked through two stacked requests in the app.
- [ ] **Claude usage meter depends on an experimental SDK call.** If an SDK update breaks it, the meter shows "—"; switch to the stable API once there is one.
- [x] **Quick-edit detection was keyword-based.** Haiku now judges each request (size, and how much suits Codex); keyword rules remain only as the fallback.
- [ ] **`npm start` apps restart after every reply.** Plain servers can't reload their own code; a few seconds each time.
